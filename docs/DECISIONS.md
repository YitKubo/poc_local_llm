# 設計判断の記録（ADR）

どの既存の仕組みを採用し、何を却下し、なぜそう判断したか。**実測で当初の想定が覆った箇所は、当初の判断を消さずに「実測による訂正」として残している。**
実測値は [RESULTS.md](RESULTS.md)、出典は [RESEARCH.md](RESEARCH.md) を参照。

## 検討の変遷（時系列）

1. ゲートウェイをフル自作する案（公平キュー・RPM/TPM・クォータ・メトリクス一式、約800〜1000行）
2. 「複雑すぎないか」→ 既製品を調査。LiteLLM 等が大半をカバーし、**公平キューだけが空白**と判明
3. 「一般的に使える仕組みは配布されていないのか」→ llm-d flow control を発見。標準の型は確立済みだが Kubernetes + GPU 前提で規模が合わない
4. 「独自実装はあまりやりたくない」→ 既製品のみの構成へ転換。CLI も `llm` に置き換え、**アプリケーションコードはゼロ**に
5. 「トークンを分散して処理する機能はないのか」→ llama.cpp の連続バッチングに着目。占有防止の主役をキューからバッチングへ（ADR-003）
6. **実装・実測 → ADR-003 の前提の一部が実測で覆った**。ゲートウェイのキー別上限は「バックストップ」ではなく必須と判明（ADR-003 訂正、ADR-006）

## ADR-001: ゲートウェイを自作せず LiteLLM Proxy を採用

- **検討した案**: ①フル自作（約800〜1000行） ②中核のみ自作（公平キュー等、約400行） ③LiteLLM Proxy ④LiteLLM + 公平キューの薄い自作前段
- **決定**: ③ LiteLLM Proxy（MIT）
- **理由**: 認証・仮想キー・RPM/TPM・`max_parallel_requests`・予算・管理UI・Prometheus がすべて既製品に存在し、自作は車輪の再発明。保守する独自コードを持たない方針を優先した。
- **放棄したもの**: キー間の公平な順番待ち。
- **代償**: 仮想キーの永続化に PostgreSQL が必要（コンテナが1つ増える）。

## ADR-002: 公平キューを自作しない

- **調査**: 公平キューは llm-d flow control（Red Hat AI Inference 3.5 で GA）が「優先度バンド + テナント間ラウンドロビン + テナント内FCFS」という型を確立している。設計を自分で発明する必要はない。
- **却下理由**: llm-d は複数レプリカの GPU クラスタ向けの記事で、1台CPUには規模が合わないと判断した。※「Kubernetes 必須」とは記事に明記されておらず、これは**私の推測**（[RESEARCH.md](RESEARCH.md) 参照）。
- **移行先候補**: 将来 GPU/k8s へ移す際は llm-d flow control を第一候補にする。
- **他に確認したもの**: Kong AI Gateway、Envoy AI Gateway。per-user のトークン制限は持つが、公平キューではなくレート制限による拒否という説明だった。

## ADR-003: 占有防止の主役を「連続バッチング」に置く（一部訂正あり）

- **当初の判断**: llama.cpp の continuous batching は既定で有効で、`--parallel N` のスロットが各デコードステップで同時にトークンを生成する。CPU はメモリ帯域律速なので、バッチ化で**合計スループットが伸びる**はず。よってスロットを潤沢に取れば待ち行列は発生せず、ゲートウェイの上限は異常時のバックストップで足りる。
- **実測による訂正（[RESULTS.md](RESULTS.md) §1）**:
  - 「合計スループットが伸びる」は**この CPU では成り立たなかった**。同時数 1→12 で合計は約 21〜28 tok/s のまま、1本あたりの速度はほぼ 1/N になった。
  - 連続バッチングが与えるのは**「全員が同時に少しずつ進む（誰かの完了を待たない）」性質のみ**で、容量の増加ではない。
  - スロット数を超えた要求は llama.cpp 内部の FIFO（投入者を区別しない）で待つ。ゲートウェイ無しで 1 人が 20 本投げると、後から来た別ユーザーの初回トークンまで **106.8 秒**かかった（RESULTS §2）。
- **訂正後の結論**: 連続バッチング（全員同時に進める）とゲートウェイのキー別同時実行上限は**両方必須**。後者は「バックストップ」ではなく、占有防止の実質的な担い手。
- **なお成り立つ部分**: 上限の内側にいる限り、別ユーザーは待たずに即座に生成を開始できる（gateway 経由で初回トークン 1.24 秒）。

## ADR-004: CLI は自作せず `llm`（Simon Willison）を採用（一部訂正あり）

- **検討した案**: ①Python + Typer で自作 ②Node + npm ③Go 単一バイナリ ④既製の `llm` ⑤`aichat`
- **決定**: ④ `llm`。`extra-openai-models.yaml` 1 ファイルで自前の OpenAI 互換エンドポイントを登録でき、`llm chat` で対話、ストリーミング既定ON、履歴はローカル SQLite。
- **当初の記述（誤り）**: 「`llm` は 429 を自動リトライしないので、ユーザーが再実行する必要がある」
- **実測による訂正**: alice の 2 スロットが埋まっている間に `llm` を実行したところ、エラーは出ず **63 秒待って正常に応答**した（終了コード 0、stderr 空）。少なくともこの条件では 429 が自動的に吸収されている。原因は使用ライブラリ側のリトライと推測しているが、コードレベルでは未確認。混雑が長く続いた場合の最終的な挙動（エラー表示になるか）も未検証。
- **導入方法**: 対象端末に `pipx` が無かったため、`setup_client.sh` は pipx が無ければ専用 venv + `~/.local/bin` へのリンクにフォールバックする。

## ADR-005: Redis を使わない

- LiteLLM の `max_parallel_requests` に Redis キャッシュ有効時の不具合報告があるため、単一インスタンス + PostgreSQL のみとした。
- ※この根拠は検索結果の Issue タイトル（#17323）のみで、**本文は読んでいない**。Redis を使わない構成自体は検証用途では不利益がないので採用した。

## ADR-006: 実測に基づくサイジング（parallel=4 / threads=6 / per-key=2）

- **`--parallel 4`**: 合計 25〜30 tok/s 前後で固定なので、スロットは容量ではなく「分け方」を決めるだけ。実用下限を 1 人 5〜10 tok/s とすると 3〜5 人。4 スロットで満員のとき 1 人あたり約 7.6 tok/s（`--parallel 4` で再計測、RESULTS §1b）、8 スロット満員では約 3.4 tok/s になり下限を割る。
  - 再計測で分かった副作用: 4 スロットで N=8 や 12 を投げると、超過分は llama.cpp 内部 FIFO で最大 19〜37 秒待つ（8 スロットなら全員が遅く同時に進む）。per-key 上限（2 本）があるので 1 人ではこの状態を作れず、3 人以上が同時に 2 本ずつ投げたときだけ起きる。
- **`--threads 6`**: 4 と 6 は誤差の範囲。**12（SMT の全スレッド）は数倍遅くなる**（N=1 で 4.6 tok/s）ので避ける。
- **`--kv-unified` を明示指定**: `--help` の記載では統合 KV は「スロット数が auto のときのみ既定で有効」。`--parallel` を明示すると既定では `-c` がスロット数で割られるため、明示した（起動ログで `kv_unified = 'true'`, `n_ctx_slot = 16384` を確認）。当初のプランの「統合KVが既定」という記述は不正確だった。
- **`max_parallel_requests = 2`**（スロット 4 の半分）: 1 人が全スロットを取れないようにする。同値にすると効かない。
- **既知の限界**: 上限を超えた分は待たされず 429 で拒否される（公平キューが無いため）。

## 未解決・今後の検討

- 上限超過時の挙動の最終形（`llm` のリトライ上限を超える長時間占有時にどう見えるか）
- 日次予算は検知が遅延する（RESULTS §4）ため厳密な上限にはならない
- 想定同時利用人数が 5 人を超えるなら、より小さいモデル（Llama-3.2-1B 等）か GPU、公平キュー付き基盤（llm-d）を検討する
