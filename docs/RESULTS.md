# 実測結果

- 環境: WSL2 / Intel Core 7 150U（12 スレッド）/ RAM 23GB / GPU なし
- モデル: Qwen2.5-1.5B-Instruct Q4_K_M（941MB）、llama.cpp server（`ghcr.io/ggml-org/llama.cpp:server`）
- 実施日: 2026-09-21
- 計測: `server/scripts/loadtest.py`（各リクエストは `max_tokens=128` のストリーミング。生成速度は初回トークン以降の tok/s）
- **注意**: WSL2 上の単発計測で、同じ設定でも数割のばらつきがある（後述）。傾向を見る資料であり、精密なベンチマークではない。

## 1. 同時接続数と速度（llama.cpp 直、`--parallel 8`、`-t 6`）

| 同時数 N | 1本あたり tok/s（中央値） | 合計 tok/s | 初回トークンまで 中央値 / 最大 (s) |
|---:|---:|---:|---:|
| 1 | 27.6 | 26.2 | 0.29 / 0.29 |
| 2 | 10.4 | 20.9 | 0.08 / 0.08 |
| 4 | 6.5 | 24.8 | 0.95 / 0.95 |
| 8 | 3.4 | 25.0 | 3.25 / 3.26 |
| 12 | 3.5 | 28.2 | 0.24 / 36.51（8 本が即開始、残り 4 本は待ち） |

**読み取り**: 合計スループットは N によらず約 21〜28 tok/s で、**連続バッチングによる伸びは見られなかった**。1本あたりはほぼ 1/N。N=12 で最大 36.5 秒待つのは、スロット 8 を超えた 4 本が内部 FIFO で待つため。
単発の短い 1 リクエスト（8 トークン）では生成 37.7 tok/s だった（同じ設定の N=1 で 27.6 → ばらつきの目安）。

### スレッド数の影響（`--parallel 8`）

| threads | N=1 1本あたり | N=4 合計 | N=8 合計 | N=8 1本あたり |
|---:|---:|---:|---:|---:|
| 4 | 15.7 | 25.1 | 28.4 | 3.9 |
| 6 | 27.6 | 24.8 | 25.0 | 3.4 |
| 12 | 4.6 | 12.6 | 14.3 | 1.8 |

- 4 と 6 は合計値が誤差の範囲。**12 は大幅に悪化**（SMT を含む全スレッドを使うと逆効果）。
- N=1 だけ 4 が 6 より遅く見えるが、単発ばらつきの範囲か有意差かは切り分けていない（下の §1b で N=1 は 17〜23 tok/s と揺れることが分かった。この差は有意とは言えない）。

## 1b. 同時接続数と速度（llama.cpp 直、**`--parallel 4`**、`-t 6`、本番設定）

| 同時数 N | 1本あたり tok/s（中央値） | 合計 tok/s | 初回トークンまで 中央値 / 最大 (s) |
|---:|---:|---:|---:|
| 1 | 17.4 / 23.0 / 18.1 / 19.5 / 21.5（5 回） | 同左 | 0.05〜0.51 |
| 2 | 12.1 | 24.3 | 0.08 / 0.08 |
| 4 | 7.6 / 7.7 / 7.5（3 回） | 28.9 / 30.8 / 29.9 | 0.12〜0.97 / 0.13〜0.97 |
| 8 | 7.5（最小 6.8） | 29.6 | 9.57 / 18.99（4 本が即開始、残り 4 本は待ち） |
| 12 | 7.6（最小 7.1） | 28.8 | 18.46 / 36.56（4 本が即開始、残り 8 本は待ち） |

**読み取り**:
- 合計は N=2 以降 **約 29〜31 tok/s で一定**。§1 の「合計は同時数で伸びない」という結論は 4 スロットでも同じ。
- **N=4 の 1 本あたりは約 7.6 tok/s で 3 回とも安定**（当初の見積もり 6.5 より少し良い）。実用下限（5〜10 tok/s）の範囲内。
- N=8, 12 では 1 本あたりは 7.5 のまま変わらず、代わりに**スロットを超えた分が待つ**（TTFT が 9.6〜36.6 秒）。8 スロット（§1）では全員が同時に進む代わりに 1 本あたり 3.4 tok/s に落ちていた。スロットを 4 に絞ると「遅く全員」ではなく「速く 4 本 + 残りは待ち」になる。待ちは llama.cpp 内部の FIFO なので投入者を区別しない。**ゲートウェイの per-key 上限（2 本）があるため、この待ちは通常運用では 1 人が作れない**（作れるのは 3 人以上が同時に 2 本ずつ投げたとき）。
- N=1 の絶対値は 17〜23 tok/s で、§1（8 スロット時の 27.6）や単発 8 トークンの 37.7 より低い。原因は未特定（WSL2 のばらつきか、スロット数の違いか、計測日時の負荷かは切り分けていない）。N=1 は 5 回で最大 23.0 と最小 17.4 の差が約 3 割ある。
- 4 スロットと 8 スロットで N=1 の値を比べる場合は、この揺れ幅（3 割）より大きい差でないと有意と言えない。

- 実施: 2026-09-21、`server/docker-compose.debug.yml` オーバーレイで llama.cpp をループバックに公開して計測後、非公開構成へ復帰。

## 2. 占有の検証（20 本同時 + 3 秒後に別ユーザー 1 本、`--parallel 4`）

| | 重いユーザー 20 本 | 軽いユーザー 1 本（3 秒後に到着） |
|---|---|---|
| **ゲートウェイ無し（llama.cpp 直）** | 20 本すべて 200。初回トークン 中央値 56.2s / 最大 92.1s | **初回トークンまで 106.79 秒**（20 本の後ろに並ぶ） |
| **LiteLLM 経由（キー別 `max_parallel_requests=2`）** | 200 が 2 本、**429 が 18 本**。初回トークン 中央値 1.43s | **初回トークンまで 1.24 秒**、7.5 tok/s、429 なし |

**結論**: キー別の同時実行上限が無いと、1 人の連投で他ユーザーが 100 秒超待たされる。上限があれば別ユーザーは影響をほぼ受けない。代償は、上限を超えた重いユーザー側が 429 になること。

## 3. 上限の挙動（LiteLLM）

- `max_parallel_requests=2` の key で staggered な 4 本の streaming: 200 が 2、429 が 2（拒否は約 25ms で返る）。メッセージは `Limit type: max_parallel_requests. Current limit: 2, Remaining: 0`。
- `rpm_limit=2` の key で 4 回連続: `200 200 429 429`。
- 通常応答のヘッダに `x-ratelimit-api_key-{limit,remaining}-{requests,tokens,max_parallel_requests}` が付く。

## 4. 予算（日次クォータ）

- `max_budget=0.000002`（名目単価 1e-7/token で約 20 トークン）の key: 4 回の呼び出しがすべて 200、**次の 5 回目で** `Budget has been exceeded! ... Current cost: 2.4e-06, Max budget: 2e-06` が返った（エラー本文の code は 429）。
- **超過の検知は遅延する**（使用量の反映が非同期のため）。日次クォータは厳密な上限ではなく「概ね」の上限として扱う。厳密さが必要なら別の手段が要る。

## 5. 永続化・管理・メトリクス

## 6. クライアント（`llm` CLI）

まず隔離した `HOME` で `client/install.sh`（当時の名前は `scripts/setup_client.sh`）を実行して検証し（pipx 無し → venv フォールバックが動作）、その後**実環境の `HOME` にも導入**した（キー `kubo` を新規発行、接続先 `http://127.0.0.1:4000`）。実環境では一発実行とパイプ入力が動作（終了コード 0、応答 1.4 秒）。

- `llm "質問"`、`echo ... | llm -s "..."`（パイプ）、`llm chat` はすべて動作（`llm chat` は隔離環境での確認。実環境では未実行）。ストリーミング応答も確認。
- 対象端末は pipx が無く、venv フォールバックで導入された。`~/.local/bin` は PATH に入っていた。
- **429 時の挙動**: alice の 2 スロットが埋まっている間に `llm` を実行 → エラーは出ず **63 秒後に正常応答**（終了コード 0）。自動的に待って再試行しているように見える。長時間埋まり続けた場合の最終挙動は未検証。

### ツール呼び出し（Agent の前提）

- 非ストリーミング: `tools` を付けて「東京の天気を、ツールを使って」と依頼 → `finish_reason: "tool_calls"`、`get_weather({"city": "Tokyo"})` を返した。
- ストリーミング（Copilot が使う形）: `delta.tool_calls` が逐次チャンクで返り、引数が分割されて届く。
- モデルが**常にツールを呼ぶとは限らない**（`client/README.md` の記述どおり、断ることがある）。上は 2 回とも呼んだが、2 回では頻度は分からない。

### プロンプト処理（prefill）の遅さ ← Agent で最も効きそうな点

| 入力トークン数 | 最初の文字まで (s) | prefill 速度 (tok/s) |
|---:|---:|---:|
| 173（ツール定義のみの短い依頼） | 約 3.0 | 58 |
| 1,127 | 27.0 | 42 |
| 4,457 | 83.0 | 54 |
| 8,897 | 150.1 | 59 |

- 入力にほぼ比例して待つ（約 42〜59 tok/s）。**Copilot の Agent が実際に送る入力の大きさは未計測**で、システムプロンプト + ツール定義 + 会話履歴 + 添付ファイルで数千トークン級になる想定は推測にとどまる。
- 2 回目以降のターンで llama.cpp のプロンプトキャッシュが効いて短縮されるかは未検証。
- これを受けて、サンプル設定の `maxInputTokens` を 12000 → 8000 にした（12000 だと約 3.5 分の計算）。
